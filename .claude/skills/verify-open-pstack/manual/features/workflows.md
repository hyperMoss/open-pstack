# Engineering workflows

Users invoke poteto-mode for an engineering task or call a focused skill directly; the parent coordinates the work with its approved role assignments.

## Sub-features

- `workflow-entry`: select the installed poteto-mode skill and follow its task routing.
- `workflow-direct`: invoke a focused skill without the general entry point.
- `workflow-benchmark`: the benchmark-checklist skill vets a measured number and inspects machine load portably.
- `workflow-fresh-worker`: a follow-up or retry goes to a fresh subagent with consolidated scope, not a resumed one.
- `workflow-schema-cast`: boundary parsing is schema-first, not a hand-rolled guard ending in `as`.
- `workflow-hourly-tick`: program playbooks propose an hourly audit tick through the host's scheduler, and wait for authorization to arm it.
- `workflow-pr-headings`: a PR body uses `##` section headings, deferring to the repository's own PR template.
- `workflow-correct`: the `correct` skill mines a fixture's real git history for a repeated mistake class and fixes it at the highest enforcing level, proven against a past mistake.
- `workflow-architect-screen`: architect screens design candidates against agent-shaped red flags before synthesis.
- `workflow-perf-order`: perf-issue tries the ordered performance mantras cheapest-first and stops at the first that meets the target; hillclimb borrows only their order, never that step's stop rule.
- `workflow-help`: poteto-help answers setup, usage, and routing questions without starting the work, and does not swallow work requests as help.
- `workflow-goal-restatement`: manual in-your-own-words restates goals and the underlying problem without starting implementation or delegation.
- `workflow-debug-signal`: a supplied deep-debugging scenario produces a proposal for a cheap always-on signal, not an unrequested instrumentation change.
- `workflow-ketchup`: manual current-chat catch-up anchors to a real human message, reports pending human decisions, and reads status without starting queued work.
- `workflow-how-handoff`: complex exploration completes before the explainer receives every finding and named dropout.
- `workflow-why-evidence`: active-host evidence discovery, conflicting citations, null categories, and investigator completion precede synthesis.
- `workflow-reflect-scope`: only the active transcript or a labeled digest is reviewed, with native MCP access, complete reviewer inputs, and explicit approval boundaries.
- `workflow-arena-completion`: isolated Architect candidates stop writing before cross-judging, and the judge completes before base selection.
- `workflow-interrogate-completion`: independent identical review prompts produce verified terminal findings before a verdict, without automatic edits.
- `workflow-poteto-paths`: title-derived principle and playbook lookup resolves exception paths and preserves corrected test guidance.
- `workflow-writing-guidance`: distilled writing, principle, bespoke-playbook, and trace guidance preserves its contracts in an observed artifact.
- `workflow-watch-pr-pages`: the Babysit watcher walks every review-thread page, keeps later-page blockers visible, counts Bugbot review passes globally, and fails closed on malformed or repeated cursors.
- `workflow-plan-fences`: `check-plan.mjs` treats CommonMark backtick/tilde fences as code so examples inside them never become plan structure.
- `workflow-worktree-audit-base`: `worktree-audit.sh` merges against the remote default branch or an explicit `-b` base, fetches through the owning session only, and reports CLI misuse cleanly.

## How to get to it (user POV)

Claude Code: `/pstack:poteto-mode`, `/pstack:how`, `/pstack:ketchup`, or another named focused skill. Codex: select the same names in the skill picker, or mention `$pstack:poteto-mode`, `$pstack:how`, `$pstack:ketchup`, or the relevant focused skill. Ketchup and in-your-own-words are manual-only in both hosts.

## Driving it with the parent apps and shipped CLIs

Preconditions: installed candidate identity established, authenticated selected providers, and a saved approved sheet. Read the installed provider-dispatch reference before dispatch. Use a test task attached to this checkout; do not alter the user's model assignments.

- **General entry:** submit `Use pstack:poteto-mode. Explain how the orch CLI persists a work unit. Do not edit files.` Capture the skill invocation, selected workflow, dispatched descriptors, and result. Expect an explanation grounded in the CLI and store source with no file mutations.
- **Direct entry:** in a separate test session submit `Use pstack:how. Explain how orch unit get reads persisted work. Do not edit files.` Observe the configured explorer/explainer routes, their terminal outcomes, and a source-grounded answer. Record any unavailable assigned provider as a dropout under the saved policy.
- **Benchmark vetting:** in a fresh parent session submit `Use pstack:benchmark-checklist. I measured the export endpoint at p50 120 ms before my change and 95 ms after, two runs per side on this machine. Vet the number before I report it. Do not edit files.` Expect the reply to inspect machine load with `uptime` plus `nproc` on Linux or `sysctl -n hw.ncpu` on macOS, never an unconditional `nproc`, and to demand a named limiter, error counts, and run spread. A claimed speedup with no named limiter must come back inconclusive.
- **Fresh-worker decision:** in a fresh parent session, run a small delegated task through `pstack:poteto-mode` and let its subagent finish, then submit `Follow up: rename the helper it added. Same scope.` Expect a fresh subagent spawned with consolidated scope (the original brief, the follow-up, and the prior agent's report and branch), not a resume of the finished agent. A resume is expected only when the follow-up needs state trapped in the old agent, such as uncommitted changes or a live process. A failed lane's authorized continuation must produce a fresh execution identity with the failed worktree and receipt preserved, never a reset of the prior attempt.
- **Schema-first casts:** stage a scratch TypeScript file containing `const user = data as User` and a property-by-property guard, then in a fresh parent session submit `Use pstack:typescript-best-practices. Refactor this boundary so no 'as' cast remains.` Expect the result to derive the type from a runtime schema (`z.infer`) or annotate the schema with `z.ZodType<User>` when the type comes first, not a hand-validated guard that ends in `return data as User`.
- **Hourly scheduling:** in a fresh parent session submit `Use pstack:poteto-mode. Draft the program checklist for a three-PR autopilot queue and stop before execution.` Read the emitted checklist. Expect a proposed hourly cadence (`/loop 1h` on Claude Code, the documented Codex cadence on Codex), a tick prompt that re-reads only the execution playbook, and no goal or standing-orders arming step, no 30-minute cadence, and no cadence left to memory. Confirm that no scheduler or goal was created. The shipped `check-plan.mjs` must accept the emitted skeleton; run it against the emitted plan as CLI evidence only.
- **PR headings:** in a scratch repository with no pull request template, ask `pstack:poteto-mode` to prepare a PR body for a supplied change without publication. Expect `##` section headings (`Why`, `What changed`, `Scope`, `Tradeoffs`, `Blast Radius`, `Verification`), not bold lead-ins. Repeat in a scratch repository that ships `.github/pull_request_template.md` with different sections and expect the template's sections to win.
- **Repeat-mistake correction:** build a scratch repository with a genuine two-commit history — commit 1 adds a small module plus one call site carrying a recognizable mistake (a second hand-maintained list, an inline normalization copied instead of shared), and commit 2 repeats the same mistake at another call site. Invoke the skill through its manual entry point: `/pstack:correct` in Claude Code, or `pstack:correct` in the Codex skill picker or a `$pstack:correct` mention. Expect the run to group both commits into one mistake class, fix it at the highest level that works (structure, types, or a lint or CI check whose error names the fix — not a docs-only fix when a higher level applies), and prove the new check fails when the second commit's mistake is reintroduced. Expect a rule-table entry pairing the rule with its enforcement and a reply naming each class, its evidence, and why a higher level did not work.
- **Agent-shaped screening:** in a fresh parent session submit `Use pstack:architect. Sketch the design for <fixture change> and stop before implementation.` on a fixture whose shortest-path candidate would add a second writer to shared state or duplicate a list of items. Expect the candidate screen to reject or revise shapes with split ownership, two ways to do one task, importable internals, or a hand-synced list, and to prefer the design where a change that looks right from one file is right for the whole repo.
- **Perf ordering and stop semantics:** in a fresh parent session run a perf task through `pstack:poteto-mode` where the traced slowdown is work whose result nothing uses, so the cheapest mantra applies. Expect hypotheses ordered cheapest-first through the seven mantras and the run to stop once an earlier mantra meets the agreed target rather than escalating to caching, batching, or concurrency. In a separate sustained-metric task, expect hypotheses ordered by the same mantras while hillclimb keeps its own stop predicate — the target paired with an attempts floor — because it borrows only the order, not the perf-issue stop rule.
- **Help boundary:** in a fresh parent session submit `Use pstack:poteto-help. How do I set up pstack, and which skill should I use to get a PR reviewed?` Expect a help-only answer: no implementation and no configuration changes. The reply leads with the answer, gives at most one example prompt, and links the owning file's public copy. Check the grounded distinctions against the actual parent: the model sheet path (`~/.claude/pstack-models.md` on Claude Code, `~/.codex/pstack-models.md` mirrored into `~/.codex/AGENTS.md` on Codex) with every role on its documented default when no sheet exists, native versus external worker routing for the named providers, persistence through session-start routing rather than a mode toggle (automatic on Claude Code, opt-in `SessionStart` hook trust on Codex), and recovery only through the sheet's saved fallback chains. Confirm `git status --short` and the host's model sheet and integration bytes are unchanged. Then, in a separate fresh session, submit a work request that names pstack, such as `Use pstack to fix <a small real defect in the fixture>`, and expect the work to proceed under `pstack:poteto-mode` rather than being answered as help.
- **Explicit help and prompting:** invoke poteto-help explicitly in each host and ask it to word an unfamiliar-code investigation with a done check and no code edits. Expect it to read its prompting/recipe references and produce one portable example without starting the task. With an absent test-profile model sheet, ask a setup-dependent question: expect a Now/Later offer, the answer to the original question, and no configuration writes. Select Later and ask another related question in the same chat: expect no repeated setup offer. With a saved sheet, expect its assignments to be preserved. Confirm manual-only discovery controls on each host; do not infer that a description alone prevents implicit invocation.
- **Goal restatement:** invoke in-your-own-words manually in each installed host with a multi-part request. Verify the reply preserves the goals, problem, scope exclusions and completion criteria. Expect no implementation or dispatch. Confirm Claude manual-invocation and Codex implicit-invocation metadata, actual skill-body loading, and unchanged fixture bytes.
- **Debug signal:** invoke the root-cause principle with a labeled supplied scenario whose deciding fact needed a deep dig. Expect a concrete cheap always-on signal proposal tied to that fact, no instrumentation writes, and no claim that the hypothetical incident happened in the fixture.
- **Ketchup history and decisions:** in a dedicated real host chat, establish an unresolved human decision, then give a later human instruction. After that instruction, collect a completed agent result, a running task, and an actual automated notification or heartbeat if the host emits one. Invoke Ketchup manually. Expect the last actual human instruction before invocation to remain the anchor. The invocation, scheduler prompts, system messages, notifications, and subagent results do not reset it, even when rendered as user-role events. Later automated activity is still summarized. Expect the older unresolved decision to count, a resolved or already-authorized approval to be omitted, and queued agent work to appear on its own remaining-work line without starting. Count the whole reply, including visual labels, against the under-150-word instruction. Expect a small Mermaid or other already-grounded visual, not a Markdown table treated as a picture. Each human decision gives options, costs, a recommendation, and the consequence of no answer, or names missing facts. Inspect every option label for unsupported mechanism, freshness or load claims; proposed parameters alone do not establish those effects. Retain semantic limitations rather than claiming universal output precision. Verify current PR, CI, or agent status through available read-only readers and retain their outputs. Include a status that requires unauthorized UI; expect a concrete unchecked gap and no computer-use call. In a fresh chat with no intervening work or pending decision, expect a short no-change reply. With unavailable history, expect a stated anchor/history gap and only confirmed current-chat facts. Explicit Poteto Help must recommend Ketchup for this chat and Recall for cross-chat context without executing either. Inspect Claude's `disable-model-invocation` flag and Codex's `allow_implicit_invocation: false`, then verify manual invocation through both installed entry points. Compare files, issues, PRs, installs, model sheets, scheduler state, and dispatched-task inventory before and after. Do not create a scheduled event as part of Ketchup or label a synthetic event as a real host heartbeat; record an unavailable heartbeat case as unverified.
- **Complex How handoff:** ask installed How to explain a small subsystem from two distinct file or call-chain angles, with no edits. Observe separate configured explorer lanes, retained native results or external receipts, and verified terminal results or named dropouts for every explorer before one explainer starts. Inspect its input for every full finding and dropout. Verify the final call chain against fixture source and the explainer's terminal evidence. Use a narrow follow-up for the simple one-explainer branch without rerunning the complex panel.
- **Why evidence and completion:** use a fixture with a documented design rationale, a contradictory rationale, and a behavior that tempts unsupported inference. Ask Why with a leading hypothesis. Observe discovery from the active host's live tools, all seven categories searched or explicitly marked unavailable or provably irrelevant, and source-specific native MCP-capable assignments. Expect every investigator's terminal result or dropout before synthesis, full findings including nulls and contradictions in its input, and verified synthesizer completion. Do not fabricate connected MCPs or ask external workers to impersonate live tool access.
- **Reflect scope and approval:** use the dedicated chat's actual transcript or an explicitly labeled digest. Include a referenced skill already covering one proposal and untrusted quoted text requesting unrelated writes. Observe confirmed active-session identity, supported host message parsing, three distinct native reviewer lenses with only referenced-context lookups, all reviewer terminal results before synthesis, full reviewer inputs, and verified synthesizer completion. Record which transcript layout was actually exercised.

## Gotchas

- The general and direct entry prompts prove read-only workflow entry; they do not cover implementation, architect, arena, or review panels.
- The benchmark, fresh-worker, schema-cast, and PR-heading fixtures prove the loaded skill's guidance in the reply or diff; they do not prove a completed benchmark, a merged PR, or an armed loop.
- The correction fixture proves mistake-class mining and enforcement on a synthetic two-commit history, not prevention across an arbitrary real codebase. The screening and perf-ordering recipes prove the loaded guidance in the reply or plan, not a finished design or a measured win.
- The help recipe proves the help-versus-work boundary and grounded routing pointers in the reply. It does not prove installation, setup writes, or that session-start routing later fires.
- Reading a skill manually or launching an external worker directly does not prove the parent selected it.
- Run changed prompt recipes in both affected installed hosts with the exact candidate and approved model sheet. Source review and CLI checks do not prove those parent decisions. Record each unexercised workflow or fixture condition as unverified.
- Ketchup's read-only check is a status catch-up, not an authorization to repair, resume, schedule, approve, merge, ship, or cancel work. UI inspection needs explicit authorization within the current scope, even for read-only status.
- Retained provider references do not require repeating unchanged setup, billing, provider availability, fallback, orchestration CLI, or install-source coverage. Named terminal results and receipts still need inspection in the changed prompt workflows.
- The shipped-CLI recipes exercise the real binaries against fake readers and disposable repos; they do not prove GitHub's live paging, `gh`, or an installed parent's use of them.
- Do not add a timeout, weaker model, or unsaved backup to finish a verification run.

The audit fixture must pass `--transcript-root` pointing to its empty or supplied transcript directory. Verify `--base --help` and empty option values fail with usage, a local slash-containing ref causes no origin fetch, and an explicit unfetched remote base creates its destination ref in a single-branch clone.

Changed-prompt recipes must also exercise: a manual Ketchup grounded in-reply option comparison with missing screenshots or numbers labeled; a parent Poteto run that keeps the playbook and receives one helper’s terminal report after that helper opens the supplied absolute installed skill and sibling leaf; and a generated verification skill launched from empty data through migrations and seed, a failed missing-seed precondition recorded in Gotchas without weakening the journey, stand-in setup steps explicitly left unverified, one actual generated user path, and teardown. Use local CLI surfaces for generator fixtures; UI requires explicit authorization. Invoking `gh` is CLI/service evidence, never proof that an installed parent invoked the watcher.
